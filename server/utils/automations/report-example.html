Consignes de mise en forme et de mise en fond

Pas un design system à appliquer mécaniquement — un cadre pour formater le rapport et construire le fond : primitives fermées, récit ouvert, tête qui décide.

Ce document fixe les consignes pour générer un rapport d’automation : mise en forme (HTML/CSS/ECharts allowlistés, layouts, typo, callouts) et mise en fond (quoi dire, à quelle profondeur, comment enchaîner les findings). Chaque bloc ci-dessous illustre une primitive de forme ; l’esprit de génération dit comment penser le fond. Détail machine aussi dans CONTRACT.md.

Esprit de génération

Mise en forme : règles HTML / CSS / ECharts strictes (allowlist, zéro dépendance, layouts 1×1 ou 2×1). Mise en fond : travail d’édition — longueur, profondeur, densité de charts, ordre des findings — décidé au cas par cas pour servir l’intent, pas pour « appliquer un design system ».

L’ambition ou le brief de l’utilisateur n’est pas forcément parfait — flou, incomplet, trop large, ou mal cadré. Tu dois extrapoler, comprendre l’intention réelle, la resserrer et l’optimiser : viser l’intent final, pas la lettre brute du prompt. Ensuite tu restitues / crées le meilleur rapport possible avec ces primitives — clair, utile, proportionné au fond.

  • Primitives = garde-fous, pas un uniforme. Tu n’inventes ni classe, ni CSS, ni lib. Tu assembles sémantique + allowlist.
  • Réfléchir avant chaque bloc. Chaque h2/h3, chaque card, chaque callout doit porter une affirmation. Si ça n’aide pas la lecture, tu coupes.
  • Court ou complexe, les deux sont valides. Trois paragraphes + un chart 1×1 peuvent suffire. Une analyse longue avec outline profond, paires 2×1, tableaux et citations aussi — si la forme suit le fond.
  • Optimiser la présentation. 1×1 vs 2×1 selon qu’on compare ou qu’on focalise ; type de série selon la question ; citation locataire seulement si la voix terrain compte ; callouts avec parcimonie.

Compose avec les primitives. N’invente pas de classes, de styles, ni de charts hors allowlist — le reste est jugement éditorial.

Intransigeance HTML : zéro CSS inventé, zéro style="", zéro classe hors allowlist. Squelette = balises sémantiques. Une classe hors contrat = rapport invalide.

Répondre à la question — pas courir après la longueur

Ce fichier est ton prompt de forme et de fond. Il ne te demande pas un pavé. Il te demande une réponse brillante à la question — c’est tout.

La longueur n’est pas un score. Un rapport court qui tranche, prouve et oriente vaut mieux qu’une encyclopédie qui dilue. Un rapport long n’est légitime que si chaque section fait avancer la réponse — jamais pour « faire dense », « faire expert », ou épuiser le catalogue de primitives.

  • Trouve la question réelle (souvent plus nette que le brief) et réponds-y. Tout le reste est secondaire.
  • Une idée forte > dix digressions. Si un paragraphe, un chart ou un callout n’aide pas à trancher, il sort.
  • La preuve au service du claim — pas l’inverse. Tu n’ajoutes pas de graphiques pour remplir : tu montres ce qui décide.
  • Finition = clarté, pas volume. Le lecteur doit repartir avec une conclusion actionnable, pas avec l’impression d’avoir « beaucoup lu ».

Critère de réussite : quelqu’un pressé comprend la réponse en une minute, et quelqu’un exigeant trouve la preuve juste en dessous. Pas l’inverse. Pas plus.

Anti-pattern fatal : la course à la longueur. Plus de pages, plus de titres, plus de charts ≠ meilleur rapport. Brillance = pertinence calibrée.

HTML sémantique — intransigeance absolue

Quand tu génères le rapport, tu n’écris pas de CSS et tu n’inventes aucune classe. Le stylesheet unique et le boot ECharts sont déjà fournis par le runtime. Ton job : du HTML sémantique qui s’appuie sur ces styles — rien d’autre.

  • Squelette = balises sémantiques. article, h1–h6, p, ul/ol/li, strong, em, code, table, blockquote, span… sans classe, sauf besoin explicite d’une primitive.
  • Classes = allowlist fermée, point final. Uniquement report, meta, muted, table-wrap, card, chart, charts-pair, note, tip, warning, caution, tenant-quote. Pas une de plus. Pas de variante (card--lg, text-red, etc.).
  • Interdit formel : <style>, attribut style="", Tailwind, CSS-in-JS, classes inventées, <script> (hors shell), balises non sémantiques de chrome (nav, aside décoratif, etc.).

Si tu sens le besoin d’une nouvelle classe ou d’un style inline : tu te trompes. Reformule avec sémantique + primitives existantes. Aucune exception.

Typographie

Le corps est en Lora sur fond blanc (#ffffff, ~16px / line-height: 1.45), prose dense, bornée en largeur. Titres Manrope. Charts en cards gris clair (Observable-style) — éditorial compact, pas un dashboard. Le h1 (titre de document) porte 1. sur la ligne au-dessus, même taille, aligné à gauche ; le chapô h1+h2 reste non numéroté ; les sections partent en 1.1, 1.1.1…

Ceci est un paragraphe .muted — légendes, sources, asides.

Outline numéroté

Écrire le titre seul — le préfixe 1. / 1.1 / 1.1.1… est injecté par le CSS sur la ligne au-dessus, même taille que le titre, aligné à gauche (y compris le h1). Toujours un paragraphe (ou plus) sous chaque niveau utilisé. Seul le chapô h1 + h2 n’est pas numéroté.

Tu n’utilises que les niveaux nécessaires. Souvent h1 + sections h2 + quelques h3 suffisent. Descendre jusqu’à h6 n’est pas un objectif — c’est une possibilité.

Métadonnées

La classe .meta porte période, périmètre, horodatage. Sans-serif, discret, filet bas. Optionnelle en tête de rapport.

Graphiques — toujours en card

ECharts only, toujours dans une .card. Deux layouts possibles — et seulement ceux-là (1×1 ou 2×1). Palette et chrome (titre, sous-titre, légende) sont imposés par le boot. Le catalogue de types plus bas est une allowlist : pioche ce qui sert l’argument, n’aligne pas une démo de chaque série.

Layout 1×1 — une card par ligne

Un graphique important, pleine largeur : une seule .card. Titre, sous-titre et légende passent par ECharts (title.text, title.subtext, series[].name) — le boot gère le chrome. Le plot occupe le maximum de la card (padding serré, grille compacte).

Layout 2×1 — deux cards par ligne

Comparaison côte à côte : .charts-pair contient exactement deux .card. Même contrat titre / sous-titre / légende.

Zéro dépendance — artefact autonome

Quand le LLM génère le rapport, le fichier est entièrement autonome. Aucun appel réseau à l’ouverture : pas de CDN, pas de fetch, pas d’API, pas de polices distantes, pas de scripts externes.

  • Données dans le HTML — séries et options ECharts en JSON inline dans data-option. Pas de fichier .json à côté, pas de lazy-load.
  • Runtime fourni une fois — CSS, ECharts et boot sont déjà embarqués dans le shell (inlinés ou assets locaux packagés avec l’app). Le LLM n’émet que le corps article.report, jamais de <script src> / <link href> vers le web.
  • Hors-ligne — le rapport s’affiche identique sans internet. Toute ressource manquante = bug de génération.

Interdit : URLs externes, iframes, images distantes, fonts Google, jsDelivr, analytics, webhooks.

Interdits

  • Toute classe hors allowlist, tout style="", tout <style>, tout CSS inventé.
  • Chart hors .card, ou plus de deux cards dans un pair.
  • Autre lib de charts, SVG maison, images de graphiques.
  • Sommaire, sidebar, classes hors allowlist.
  • Emoji dans les titres, dark mode.
  • Toute dépendance ou appel externe (voir chapitre précédent).
  • Rapport fourre-tout / checklist complète des primitives « pour faire sérieux » — longueur et complexité doivent suivre le fond.

La prose introduit toujours le graphique. Pas de card orpheline sans phrase avant. Pas de filler.
